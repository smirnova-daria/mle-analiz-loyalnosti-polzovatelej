# Анализ лояльности пользователей Яндекс Афиши

Исследовательский проект: анализ поведения пользователей Яндекс Афиши
и выявление признаков, связанных с повторными заказами. Логика исследования,
изначально собранная в Jupyter Notebook, перенесена в Python-приложение
с разделением на модули и ООП-структурой.

## Что делает проект

По выгрузке заказов из БД `data-analyst-afisha` приложение:

1. Загружает данные и курсы валют.
2. Приводит выручку к рублям, чистит данные (типы, дубликаты, выбросы).
3. Строит профиль пользователя (дата первого/последнего заказа, устройство,
   регион, тип мероприятия, число заказов, средняя выручка, среднее число
   билетов, средний интервал между заказами).
4. Считает retention по сегментам первого заказа.
5. Проверяет две продуктовые гипотезы (спорт vs концерты; топ-регионы vs
   остальные).
6. Считает корреляции φ_K между признаками профиля и числом заказов.
7. Печатает краткий итоговый отчёт в терминал.

## Установка и запуск

### 1. Клонировать репозиторий

```bash
git clone https://github.com/smirnova-daria/mle-analiz-loyalnosti-polzovatelej.git afisha-loyalty
cd afisha-loyalty
```

### 2. Создать виртуальное окружение и установить зависимости

```bash
python3 -m venv venv
source venv/bin/activate          
pip install -r requirements.txt
```

В **Windows**, если команда `python3` недоступна, используйте `python`:

```bash
python -m venv venv
source venv\\Scripts\\activate
pip install -r requirements.txt
```

### 3. Настроить переменные окружения

Создайте `.env` из шаблона и заполните доступы к БД:

```bash
cp .env.example .env
```

В `.env` должны быть переменные:

```
DB_USER=...
DB_PWD=...
DB_HOST=...
DB_PORT=...
DB_NAME=...
```

Файл `.env` не коммитится (см. `.gitignore`). В репозитории хранится только
`.env.example` без реальных значений.

### 4. Подготовить данные

Проект использует файл, который **не хранится в репозитории** (папка
`data/` в `.gitignore`):

| Файл | Откуда взять | Куда положить |
|---|---|---|
| `final_tickets_tenge_df.csv` | [code.s3.yandex.net/datasets/final_tickets_tenge_df.csv](https://code.s3.yandex.net/datasets/final_tickets_tenge_df.csv) | `data/final_tickets_tenge_df.csv` |

Папка `data/` должна существовать локально перед запуском.

### 5. Запустить приложение

```bash
python3 main.py
```
В **Windows**, если команда `python3` недоступна, используйте:

```bash
python main.py
```

В терминал выводится краткий отчёт: объём данных, retention по сегментам,
результаты гипотез, ключевые φ_K и рекомендации.


## Данные и предобработка

- **Период:** 1 июня — 31 октября 2024 года.
- **Объём:** 290 611 заказов, 21 933 пользователя, 22 427 мероприятий.
- **Выручка:** тенге (≈ 1,7% заказов) переведена в рубли по курсу на дату
  заказа; создан столбец `revenue_rub`.
- **Чистка:**
  - удалены дубликаты по содержательным полям заказа (40 строк, 0,01%);
  - удалены заказы с отрицательной выручкой (381 строка);
  - удалены заказы выше 99-го перцентиля выручки (2 825 строк, 0,97%);
  - в профиле отфильтрованы аномально активные аккаунты выше 99-го
    перцентиля по числу заказов (216 пользователей, 0,99% — но 51% всех
    заказов).
- **Итог:** 287 365 заказов, 21 622 пользователя.

## Основные результаты

- **Структура аудитории.** 83% первых заказов — с мобильных устройств;
  44% — концерты; 50% пользователей — из Каменевского региона или
  Североярской области. Медиана — 2 заказа, среднее — 6,5 (после удаления
  аномальных аккаунтов).
- **Возвраты.** 61,3% пользователей сделали 2+ заказа; 38,7% остановились
  на одном.
- **Retention по сегментам первого заказа:**
  - устройство: `desktop` — 64,0%, `mobile` — 61,0%;
  - тип мероприятия: театр — 63,0%, выставки — 64,0% (мало данных),
    концерты — 62,0%, спорт — 56,0%;
  - регион: топ-10 — 62,5%, остальные — 58,2%.
- **Гипотеза 1 (спорт vs концерты):** не подтверждена. Спорт возвращается
  реже концертов на 6,0 п.п. (55,8% против 61,8%).
- **Гипотеза 2 (топ-регионы vs остальные):** подтверждается частично.
  Топ-10 регионов удерживают на 4,4 п.п. лучше, но эффект неустойчив.
- **φ_K:** сильнее всего с числом заказов связаны `avg_tickets` (0,23 на
  непрерывном признаке, 0,34 на сегментах) и `avg_revenue_rub` (0,22 и 0,28).
  Однако эти признаки вычисляются постфактум по всем заказам, поэтому их
  связь отчасти механическая. Признаки первого заказа (устройство, тип
  мероприятия, регион, день недели) связаны с числом заказов слабо (≤ 0,1).

## Рекомендации для Яндекс Афиши

1. **Сфокусироваться на втором заказе.** ~39% пользователей не возвращаются.
   Окно удержания — ориентировочно 1–3 недели после первой покупки
   (медиана среднего интервала между заказами — 8,5 дня; точное время до
   второго заказа требует отдельного расчёта).
2. **Приоритет удержания:** пользователи с первым заказом на **театр** и
   с **десктопа** — эти сегменты устойчиво возвращаются выше среднего.
3. **Дополнительные усилия:** мобильные пользователи (83% входов, но
   возвращаются реже среднего) — нужны стимулы к повторной покупке.
4. **Не сегментировать по дню недели и региону** — эффект слабый и
   неустойчивый; в 39 регионах из 81 меньше 50 пользователей, выводы по ним
   ненадёжны.
5. **Отдельная стратегия для аномальных аккаунтов** (216 пользователей —
   51% заказов): определить, это боты, перекупщики или B2B-клиенты, и
   исключать их из метрик удержания обычных клиентов.
6. **При построении модели возврата:**
   - использовать целевую переменную «повторный заказ в течение N дней»
     вместо «2+ заказа»;
   - не включать признаки, посчитанные по всем заказам пользователя
     (`avg_revenue_rub`, `avg_tickets`, `total_orders`) — они известны
     только постфактум и дают механическую связь с целевой переменной;
   - использовать только признаки, доступные на момент прогноза:
     устройство, тип мероприятия, регион, день недели, чек и число билетов
     **первого** заказа;
   - добавить данные о канале привлечения и поведении после первого заказа.
7. **Спорт и ёлки** — сезонные сегменты с малым числом пользователей;
   гипотеза о высоком возврате спортивных зрителей не подтверждена.
   Перепроверить на периоде не менее 12 месяцев.
